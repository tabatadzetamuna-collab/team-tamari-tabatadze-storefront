# ADR-0007: API-ის სურათები და მათი ზომა

## Status
მიღებული

## Context
FE-010: Lighthouse Mobile-ზე Performance ≥ 85. API პროდუქტის სურათს ყოველთვის **700 × 700** JPEG-ად აბრუნებს (~45–75 KB), სხვა ზომას ვერ ვითხოვთ — ამიტომ `srcset`-ს ვერ ავაწყობთ. კატალოგის ბარათში სურათი მობილურზე ~383 px-ია (DPR-ით), გალერეის მინიატურებში — კიდევ უფრო პატარა.

გაზომვა (2026-10-30, Slow 4G): კატალოგი 8 სურათს ტვირთავს — 465 KB, აქედან Lighthouse-ის შეფასებით **324 KB ზედმეტია**; პროდუქტის გვერდზე — **519 KB**. კატალოგის Performance-ის მედიანა 76-ია, LCP ელემენტი — პირველი ბარათის სურათი.

## Decision
რაც ჩვენს ხელშია:
- ყველა `<img>`-ს CSS-ში `aspect-ratio: 1 / 1` — ჩატვირთვისას ლეიაუთი არ ხტება (CLS 0).
- ეკრანს ქვემოთ მყოფი სურათები — `loading="lazy"`; კატალოგის პირველი რიგი (2) და პროდუქტის მთავარი სურათი — `lazy`-ის გარეშე, `fetchPriority="high"`.
- `preconnect` API-ის დომენზე — ორი: `crossorigin`-ით (fetch) და მის გარეშე (სურათები).
- პროდუქტის მონაცემი იწყება აპის გაშვებისთანავე (`prefetchQuery`) — სურათის URL ადრე ვიცით.
- ჩვენი სურათები: ლოგო — SVG `width`/`height`-ით; ავტორიზაციის ფონი — WebP (572 → 88 KB).

რაც არ არის ჩვენს ხელში — სურათის ზომა. ჩავწერეთ და დავტოვეთ.

## Consequences
- კატალოგს Performance 85-მდე ძირითადად სურათების ზედმეტი 324 KB აკლია; გაშვებებს შორის რყევა (73–83) გარე სერვერის (Render) სიჩქარეზეა დამოკიდებული.
- ქულის „მოტყუება“ (ნაკლები ბარათი, სურათის დამალვა) არ გამოგვიყენებია.
- **სწორი გადაწყვეტა:** სერვერმა ზომის ვარიანტები უნდა დააბრუნოს (მაგ. 300 / 700 px) ან სურათები image CDN-ით გაიცეს (`?w=400&format=webp`). მაშინ ფრონტზე `srcset` + `sizes` დაემატება და ბარათი ~15–20 KB-იან სურათს ჩამოტვირთავს ~75 KB-ის ნაცვლად.
- სურათებს სერვერი 7-დღიან ქეშს აძლევს — განმეორებით ვიზიტზე ეს პრობლემა აღარ ჩანს (კალათა: Performance 100).
